# Loco architecture

This repository moved from a hand-rolled `sqlx` + `sea-query` + `Engine`-generic data layer to [Loco](https://loco.rs) (SeaORM `DatabaseConnection` for query execution, `sea-orm-migration` for schema).
See `yotsunagi/yorishiro#221` for the rationale.

**`yorishiro-specs`' `Yorishiro_v1_technical_spec*.md` documents are not being updated slice by slice during this rebuild**, a deliberate deferral rather than drift: they describe the shipped v0.50.0 behavior, which is still what a reader of those documents needs until `develop` actually merges and replaces it.
They get brought current as part of that merge, not each commit here.

**`import_jsonl` attributes every imported entity to the importing key's own `user_id`, never to the exported `created_by`.**
The old code passed `entity.created_by` straight through unremapped, which only ever worked because every restore it ran happened to target the same deployment that minted that user.
A restore into a different tenant hits `fk_content_entities_created_by` immediately, and `yorishiro_app` has no grant to even check `identity_users` for existence first.
Attributing to the importer is always FK-safe, and for the common case (an owner restoring their own backup into the same deployment) still names the right person.
`updated_by` was never populated by import either way (`content_entities::create` doesn't take one).

**Before writing any Loco/SeaORM code, check the actual behavior against Loco's own documentation or source (`https://loco.rs/docs/`, DeepWiki on `loco-rs/loco` and `SeaQL/sea-orm`) rather than assuming from a general Rails/ActiveRecord mental model.**
Several assumptions turned out wrong when checked: `ColType` has no primary-key-with-custom-default variant (`uuidv7()` on a UUID PK needs raw `sea_query::ColumnDef`, not a `ColType` helper); `sea-orm-cli`'s pgvector support is a compile-time feature of the installed binary, not something the app's own `Cargo.toml` features reach; the schema builder has no PostgreSQL schema-namespace, RLS, or GRANT support at all (raw SQL via `execute_unprepared` is loco's own documented answer, not a workaround).

**Repository layout**: a single Loco app crate at the repository root (package name `yorishiro-core`, binary `yorishiro_core-cli`), not `crates/yorishiro-core` + `crates/yorishiro-server`.
Migrations live in the `migration/` crate.
`ee/` still composes on top; see `ee-composition.md`.

**Schema namespace**: the old two-schema split (`identity.*`, `content.*`) is retired.
Every table lives in `public`, with the old schema name kept as a table-name prefix (`identity_workspaces`, `content_entities`), since Loco's schema builder has no PostgreSQL schema-namespace support.
**GRANT is always per-table, never schema-wide**: `migration/src/helpers.rs::grant()` exists specifically to make a schema-wide/wildcard grant structurally awkward to write, because unifying the schema means a wildcard grant would now also sweep in tables that must stay ungranted (`identity_tenants`, `identity_users`, `identity_tenant_memberships`, `identity_invites`, `identity_templates`, `identity_workspace_llm_keys`, `identity_workspace_embedding_keys`).
Never write `GRANT ... ON ALL TABLES IN SCHEMA public`.

**Migrations**: one file per table under `migration/src/`, generated via `cargo loco generate migration Create<Name>` then hand-edited.
Column definitions use `loco_rs::schema`'s `ColType` helpers where they fit; drop to raw `sea_query::ColumnDef` (see `migration/src/helpers.rs`'s `uuidv7_pk()`) for anything `ColType` can't express, rather than fighting the abstraction.
RLS, GRANT, `CREATE SCHEMA`, extensions, triggers, and `SECURITY DEFINER` functions go through `manager.get_connection().execute_unprepared(...)`: this is Loco's own documented pattern for these, not an escape hatch to avoid.

**Models**: `src/models/_entities/` is generated by `cargo loco db entities` and never hand-edited (a diff there means the migration changed and entities need regenerating, not that the file itself was wrong).
Business logic goes in `src/models/<table>.rs`, which wraps the generated `Entity`/`Model`/`ActiveModel`: reads on `impl Model`, writes on `impl ActiveModel`, everything else (custom finders, multi-step operations like key issuance) on `impl Entity`.

**The SeaORM entity API is the default on every path, control-plane and RLS-scoped tenant CRUD alike.**
`content_entities`/`content_schemas` CRUD reached from a request handler goes through `Entity::find()...`/`ActiveModel`/`Set(...)` exactly like control-plane code does, on the `DatabaseTransaction` `Authorized::txn()` hands the handler.
Raw SQL (`execute_unprepared`/`execute_raw` on that same transaction) stays only for what the entity layer genuinely can't express: JSONB containment (`data @> filter`), pgvector similarity search, and `pg_advisory_xact_lock`.
Free functions living in `src/models/<table>.rs` below that table's entity impls (`get_active_schema`, `is_schema_pending`, `entities::create`/`get`, and so on) take `&impl ConnectionTrait` so the same function works whether the caller holds a `DatabaseTransaction` or Loco's own `ctx.db`.

**A write handler must call `Authorized::commit()` before returning `Ok`, or the write silently vanishes.**
`Authorized<R>::txn()` is a `DatabaseTransaction`, which rolls back on drop; a handler that inserts a row and returns `201` without committing looks identical to a working handler in every test that only checks the status code, and the row is gone.
A read-only handler needs no commit: dropping an uncommitted, nothing-written transaction is a no-op.
Verification for any new write handler must include a follow-up read confirming the row is actually there, not just that the write call returned `Ok`.

**RLS / two-pool architecture**: Loco's own `ctx.db` (`sea_orm::DatabaseConnection`) is built from `ConnectOptions`, which has no `after_connect`/`after_release` hook, so it cannot carry the `SET ROLE`/`set_config(...)` session-state lifecycle this deployment's row-level security depends on.
`src/db.rs` builds a separate raw `sqlx::PgPool` (`TenantDb`) with that lifecycle, plus a plain `identity` pool for control-plane access (signup, setup, admin CLI, bypassing RLS via the migration role).
`TenantDb` also wraps its own pool as a `sea_orm::DatabaseConnection` (`SqlxPostgresConnector::from_sqlx_postgres_pool`), which does not remove the wrapped pool's `after_connect` hook: that hook is a property of the underlying `sqlx::PgPool`, not of SeaORM's wrapper around it.
`TenantDb::begin_for_workspace(tenant_id, workspace_id)` begins a transaction on that wrapped connection and sets `app.current_tenant`/`app.current_workspace` transaction-locally (`set_config(..., true)`), so RLS policies see them for every statement on that transaction, entity API and raw SQL alike, and they disappear automatically at commit or rollback with no `after_release` reset needed for the GUCs specifically.
Both pools are constructed in `Hooks::after_context` (`src/app.rs`) and stored as `db::DbHandle` in `ctx.shared_store`, retrieved via `ctx.shared_store.get_ref::<db::DbHandle>()`.
`Authorized<R>`'s extractor calls `begin_for_workspace` and hands the handler the resulting `DatabaseTransaction`.
`SessionLock` (session-scoped `pg_advisory_lock`, used where a caller needs the same lock held across steps that can't share one transaction) is the one thing that still has no SeaORM equivalent and stays on the raw `sqlx::PgPool` permanently: `begin`/entity API re-acquire a connection per call or pin one only for a transaction's lifetime, and neither expresses "hold this one connection across steps with no enclosing transaction."
See <https://github.com/yotsunagi/yorishiro/issues/221> for the design history.

**Decided (2026-08-24): the migration crate targets SQLite as well as PostgreSQL; nothing else does yet.**
SQLite is scoped to a single tenant with no database-enforced isolation, so it is positioned for trying Yorishiro out or personal use, never for hosting multiple tenants; application-level filtering that fakes RLS is explicitly not the answer (a single missed filter is a silent isolation break).
Every migration file calls `manager.get_database_backend()`-aware helpers in `migration/src/helpers.rs` (`enable_rls_with_policy`, `grant`, `pg_only`, `sqlite_only`, `create_table_with_checks`, `uuidv7_pk`) rather than branching on the backend itself; a migration file's own PostgreSQL statements read exactly as they did before SQLite support existed.
Roles, GRANT, RLS, and the `authenticate_api_key` SECURITY DEFINER function have no SQLite counterpart at all (nothing to protect on a single-tenant single-file database); `uuidv7()` likewise has no SQLite equivalent, so `id` columns on that backend carry no default and every insert must supply its own id.
A few things SQLite can express need a second implementation rather than a skip: a table-level CHECK constraint moves inline into `CREATE TABLE` (SQLite's `ALTER TABLE` supports only rename/add-column/drop-column, no `ADD CONSTRAINT`) via `create_table_with_checks`; the `plpgsql` trigger that detaches a schema from a deleted template gets a SQLite-syntax equivalent via `sqlite_only`; `identity_templates.tags` (`TEXT[]` on Postgres) becomes a JSON-encoded `TEXT` column on SQLite.
Vector search (pgvector/HNSW) and full-text search (`pg_trgm`) are not ported to SQLite yet: `content_entities` has no `embedding` column at all on that backend, and `docs/sqlite.md` has the details.
`src/db.rs`/`Hooks::after_context` remain PostgreSQL-only (a raw `sqlx::PgPool`); wiring the running application to actually connect to a SQLite file is separate, not-yet-done work.

**Decided (2026-08-25): `db::lock_for_update` no-ops on SQLite; `tenancy::create_tenant` hardcodes a single-tenant cap there, ignoring `YORISHIRO_MAX_TENANTS`.**
`lock_for_update` cannot retrofit SQLite's `BEGIN IMMEDIATE` itself: every call site already holds a `DatabaseTransaction` handed in from outside (`Authorized::txn()` or an explicit `.begin()` upstream), and SeaORM's SQLite transaction mode is chosen once at `.begin()` time (`TransactionOptions::sqlite_transaction_mode`, reached via `begin_with_options`), not something a helper deep inside an open transaction can select.
The no-op is race-safe anyway, not merely convenient: SQLite allows only one write transaction at a time, so a transaction that read a stale count and then tries to commit after a different transaction has since written and committed gets `SQLITE_BUSY` and the whole transaction fails, never partially applying.
See `lock_for_update`'s own doc comment for why this covers every caller in the codebase, including the `ee/` ones that write more than one row per transaction, not just the single-write count-then-insert shape.
The tenant cap is hardcoded to 1 rather than clamped against `YORISHIRO_MAX_TENANTS`, because raising that variable is a way to loosen a configurable policy, and the SQLite cap exists because RLS itself is absent, not because of policy; it must not be configurable away.
`identity_tenants::ActiveModel::id`'s generation on SQLite (that column's `uuidv7()` default is Postgres-only) moved into `ActiveModelBehavior::before_save` in the following "Decided" entry below; `create_tenant` itself no longer sets `id` directly.
Tests live in `src/models/tenancy.rs`'s own `#[cfg(test)] mod tests` (not `tests/requests/`, which is Postgres-only): each spins up its own in-memory SQLite `DatabaseConnection` via `migration::Migrator::up`, and both are `#[serial]` since they share the process-wide `YORISHIRO_MAX_TENANTS` env var.

**Decided (2026-08-25): the application boots against a SQLite file and serves `POST /setup` through `GET /api/whoami`; every other authenticated route is still unported.**
`Hooks::after_context` (`src/app.rs`) skips building `DbHandle`/the default `Authenticator` entirely when `ctx.db.get_database_backend() == DatabaseBackend::Sqlite`, rather than attempting the PostgreSQL pool construction and expecting it to fail fast: `sqlx::postgres::PgPoolOptions::connect` on a `sqlite://` URL does not error, it hangs indefinitely (confirmed by direct probe), so reaching that code path on this backend at all would hang the boot with no diagnosable error.
Every `uuidv7()`-defaulted `id` column (`identity_tenants`, `identity_workspaces`, `identity_users`, `identity_tenant_memberships`, `identity_api_keys`) now generates its own id on SQLite through `ActiveModelBehavior::before_save`, which unconditionally calls `db::sqlite_generated_id(db, self.id)` (a no-op when `id` is already `Set` or the backend is PostgreSQL, `Uuid::now_v7()` otherwise).
This does not cover `Entity::insert(active).on_conflict(...).exec(conn)`: that builder path does not call `before_save` at all (confirmed against `sea-orm` 2.0.2's source), so `tenancy::add_member`, the one call site using it, sets `id` explicitly via the same helper instead of relying on the hook; a future `on_conflict` insert needs the same explicit treatment.
`AuthContext`'s `FromRequestParts` impl (`src/controllers/extractors.rs`) branches the same way `after_context` does: on SQLite it calls new `authenticate_sqlite`/`touch_last_used_sqlite` functions (`src/services/auth/authenticate.rs`), a SeaORM entity-API replica of the Postgres `authenticate_api_key` SECURITY DEFINER function's single-argument semantics (only a workspace-scoped key resolves), reasoned the same way as the migration-level SECURITY DEFINER decision above: RLS is what that function exists to bypass, and SQLite has no RLS, so there is nothing to bypass and a direct query suffices.
`Authorized<R>`, `AuditAuthorized`, and `Verified<R>` were deliberately left untouched at this stage and still call `db_handle()` unconditionally, so every route using them answered `DbHandle missing` on SQLite; only `AuthContext` (no scope, no transaction) had a SQLite branch, matching `/whoami`'s own requirements and no further. (Superseded by the following "Decided" entry, which extends `Authorized<R>`/`AuditAuthorized`.)
`config/sqlite.yaml` is a manual-verification-only environment (`LOCO_ENV=sqlite`), not wired into any test suite (`tests/` stays PostgreSQL-only, since `request_with_create_db` issues `CREATE DATABASE`, which SQLite has no equivalent for); acceptance for this entry was empirical, not test-suite-driven: a live `POST /setup` returning `201` and a live `GET /api/whoami` returning `200` with matching ids, both confirmed with `sqlite3` CLI row-count/column checks against the actual file, plus a live `POST /auth/signup` past the cap returning `409` with the SQLite-specific remedy message.

**Decided (2026-08-25): `Authorized<R>`/`AuditAuthorized` gained SQLite branches; `Verified<R>` deliberately did not.**
`authorize_sqlite`/`authorize_audit_sqlite` (`src/services/auth/authorize.rs`) mirror `AuthContext`'s existing SQLite branch: authenticate against `ctx.db` directly, then `ctx.db.begin()` a plain (deferred) transaction rather than `TenantDb::begin_for_workspace`, since there is no RLS session state to scope on this backend.
`Verified<R>` got no branch: its one caller (`search_entities`) calls `db_handle()` unconditionally regardless, and `content_entities` was not yet reachable on SQLite at the time this entry was written (see the following "Decided" entry), so a branch here would dead-end at that call with nothing gained.
`Authorized<R>`/`AuditAuthorized` hold one connection open on a transaction for the request's duration while `touch_last_used_sqlite` acquires a second, independent connection from the same pool: the same split Postgres's `authorize`/`touch_last_used_on` use, and for the same reason (a read-only handler drops its transaction without committing, so updating `last_used_at` there would roll back with it).
This makes every such request need 2 connections at once; at `max_connections: 1` the second acquire has none to get and waits out `connect_timeout`.
`db::require_min_sqlite_connections`, called from `after_context`, rejects boot outright when `max_connections < 2` on SQLite rather than letting an operator discover this as an intermittent `500` under load.
Measured before the guard existed, at `max_connections: 1`: a read-only route still returned `200` (the failed `last_used_at` update is best-effort, logged not propagated), while a route needing a real second write (`set_maintenance`, writing through `ctx.db` independently of the held transaction) failed with `500` after ~500ms, logged as `Connection pool timed out`.
`config/sqlite.yaml` ships `max_connections: 10`.

**Decided (2026-08-25): embedding provider resolution is workspace-aware, through a seam base declares and `ee/` implements; assigning a workspace's own provider is an `ee/`-only decision.**
`WorkspaceEmbeddingResolver` (`src/services/embedding/mod.rs`) is a trait with one method, `resolve(conn: &sea_orm::DatabaseConnection, workspace_id) -> Result<Option<Arc<dyn EmbeddingProvider>>, YorishiroError>`, matching `Authenticator`'s seam shape but taking `&sea_orm::DatabaseConnection` rather than `&DbHandle`: `DbHandle` does not exist on SQLite, and unlike `Authenticator` (a PostgreSQL/RLS-only concept), this seam must resolve on both backends.
`Ok(None)` means "this workspace has no assignment of its own," which the caller (`controllers::extractors::resolve_embedding_provider`) reads as "fall back to the deployment-wide provider already in `shared_store`" rather than the seam constructing that fallback itself: building it (an ONNX model load can be hundreds of megabytes) is a cost worth paying once, not on every resolution whether or not a workspace override exists.
`DefaultEmbeddingResolver` (base's own implementation, installed unconditionally in `after_context` on every backend) always returns `None`, so an existing deployment that installs nothing extra is unaffected.
No caching: `resolve` runs once per call, the same shape `identity_workspace_llm_keys::get` already accepts for LLM inference credentials.

`ee/`'s `identity_workspace_embedding_keys` table (no RLS, no GRANT, read through `ctx.db`, matching `identity_workspace_llm_keys`) and its `EmbeddingKeyResolver` are the paid-edition decision: which workspace points at which compute backend is tenant-level policy, the same reasoning that keeps `llm_keys` in `ee/` rather than base.
`embedding_keys::set` (`ee/crates/yorishiro-hosted/src/models/embedding_keys.rs`) checks a new provider's `dimensions` against the workspace's own stamped `identity_workspaces.embedding_dimensions` at assignment time, refusing a mismatch with `ValidationFailed` before anything is stored; this is in front of `sync_embedding`'s existing write-time guard (`src/services/embedding/sync.rs`), not a replacement for it, since a workspace created before either check existed, or one assigned by direct database access outside this endpoint, still needs the write-time check to catch what assignment-time validation didn't see.

`setup.rs` and `workspaces.rs::create_workspace` were deliberately left calling the deployment-default `embedding_provider(&ctx)` unchanged: both only stamp a new workspace's initial `embedding_dimensions`/`embedding_model` from the deployment default, and a workspace-specific assignment (if any) is something an operator adds afterward through the `ee/` endpoint, not something a fresh workspace needs at creation time.
`resolve_embedding_provider` is the function that reaches the seam; the three callers that resolve a provider for a workspace's own work (`controllers::search`, `services::mcp::search`, `workers::embedding_sync`) all call it instead of `embedding_provider(&ctx)`.

**`Hooks::after_context` runs before `db::converge` applies migrations** (confirmed against `loco-rs` 1.1.0's `boot.rs`: `create_context` calls `H::after_context`, and `create_app` runs `db::converge` only after `create_context` returns).
Nothing in `after_context` may assume a migration-created object exists yet.
`TenantDb::connect`'s `after_connect` hook requires the `yorishiro_app` role, which a migration creates, so the pool it builds there is `connect_lazy` rather than `connect`: opening no physical connection at construction time defers `SET ROLE` until first use, by which point migrations have already run.

**Decided (2026-08-25): a backend branch inside a `src/models/` function stays internal to that function.**
It never changes the type the function returns, never turns into an `Err` on one backend where the other backend succeeds, and never requires the function's own callers to branch on the backend themselves.
`db::sqlite_generated_id` (returns the same `ActiveValue<Uuid>` either way), `db::lock_for_update` (returns `Ok(())` as its SQLite no-op rather than an error, matching the `Result<(), DbErr>` the PostgreSQL path also returns), and `tenancy::create_tenant`'s tenant-cap and error-message branches (both produce the same `Option<i32>`/`String` types on either backend) all hold to this, and every caller of all three calls them identically regardless of backend: `crate::db::sqlite_generated_id(db, self.id)` appears unchanged in eleven `before_save` impls, `crate::db::lock_for_update(conn, key).await?` appears unchanged at every one of its eight call sites, and `tenancy::create_tenant(&txn, name).await?` at both of its two.
`content_entities`'s SQLite fix (below) is a wider example of the same rule, not an exception to it.

**Decided (2026-08-25): `content_entities`'s SQLite gap (the `embedding: Option<PgVector>` column that doesn't exist on that backend's table) is closed for the eight functions in `src/models/content_entities.rs` that query the table directly: `count`, `get`, `get_batch`, `list`, `export_all`, `create`, `update`, `delete`.**
The `select_only().columns([...])` rewrite the previous "Decided" entry above once rejected (ten PostgreSQL request-hot-path functions touched, a worse silent-omission failure mode on a future column) turned out to be the wrong shape rather than the wrong idea: `select_record_columns` applies that column list only inside the SQLite branch of each function, leaving the PostgreSQL branch (an unrestricted `Entity::find()`, unchanged from before this entry) untouched, so neither of the original objections apply on that backend.
`EntityRecord` (this file's read-facing row type, already distinct from the generated `Model`) gained `#[derive(sea_orm::FromQueryResult)]` so `select_record_columns`'s SQLite branch can be deserialized directly into it, skipping `Model` (and its `embedding` field) entirely on that backend; `FromQueryResult`'s derive reads only the fields `EntityRecord` declares, so the same `.into_model::<EntityRecord>()` call also works unchanged on the PostgreSQL branch's wider, unrestricted row.
`count` needed the same treatment though it returns no columns of its own: `PaginatorTrait::count` wraps whatever `SELECT` it's given in a `COUNT(*)` subquery, so an unrestricted `Entity::find()` still names `embedding` in that inner query and still fails on SQLite even though the outer count never reads it.
`create`/`update` needed a second, unrelated fix on top of `select_record_columns`: `ActiveModelTrait::insert`/`update` decode their return value as a full `Model`, and SeaORM's `TryGetable` impl for `pgvector::Vector` unconditionally errors on any SQLite row (`Vector unsupported by sqlx-sqlite`, confirmed in `sea-orm` 2.0.2's source), regardless of whether the column exists or the value is set: a type-decode failure, not the "no such column" query failure every other function here hits, so it needed a different fix, not the same one applied twice.
`insert_and_fetch` routes around that decode on the SQLite branch by using `Entity::insert(active).exec_without_returning` (a row count, not a `Model`) followed by a `select_record_columns` read-back; the PostgreSQL branch still calls `active.insert(conn)` exactly as before.
That builder path doesn't call `ActiveModelBehavior::before_save`, the same gap `tenancy::add_member`'s `on_conflict` insert already had to work around (see the 2026-08-25 SQLite-boot "Decided" entry above), so `insert_and_fetch` calls `db::sqlite_generated_id` directly rather than relying on the hook to generate the id.
`update_and_fetch` uses `active.update_without_returning(conn)` instead, not the matching `Entity::update(active).exec_without_returning` builder call: that builder path skips `before_save` the same way `Entity::insert(...)` does, and `content_entities::update`'s own `ActiveModel` literal never sets `updated_at` itself (only `before_save` does, when it runs), so the first version of this fix shipped with `updated_at` silently staying stale on every SQLite update, caught by CodeRabbit's review of the PR that introduced it and confirmed by a failing assertion added to the same test that already covered every other function here. `ActiveModelTrait::update_without_returning` (unlike the raw `Entity::update(...)` builder) still calls `before_save` before executing (confirmed against `sea-orm` 2.0.2's source), so it gets the `updated_at` stamp for free without needing the `Model`-decode `update`/`insert` can't survive on SQLite. There is no `insert_without_returning` equivalent on the insert side, which is why `insert_and_fetch` still has to call `sqlite_generated_id` directly instead of reaching for the same shortcut.
`delete` turned out not to need a SQLite branch at all: `Entity::delete_many()...exec()` returns a bare row count with no column decode of any kind, confirmed by the same test that exercises the other seven.
`neighbors_batch` (`content_relations.rs`) was previously attributed to this same `embedding` gap; that attribution was wrong. Its raw SQL never selects `embedding`, and it remains broken on SQLite for an unrelated, pre-existing reason: `Statement::from_sql_and_values` hardcodes `DatabaseBackend::Postgres` and the query itself uses `unnest($2::uuid[])`, a PostgreSQL-only array function. Fixing the `embedding` gap does not fix `neighbors_batch`.
`migration_dry_run` already used `select_only()` with an explicit column list before this entry and was never affected by the `embedding` gap in the first place.
`snapshot` (`INSERT ... SELECT` against `content_entity_snapshots`) and `undo_job` (calls `active.update(conn)` directly, not through `content_entities::update`) were out of scope for this entry: `snapshot` is raw, hardcoded-Postgres SQL like `neighbors_batch`, and `undo_job`'s own `active.update(conn)` call hits the same `pgvector::Vector` decode failure `create`/`update` did, unfixed as of this entry.
Tests: `src/models/content_entities.rs`'s own `#[cfg(test)] mod sqlite_tests`, an in-memory SQLite database seeded with a tenant/workspace/schema via raw SQL, exercising all eight functions in one pass; the existing PostgreSQL-backed `tests/` suite (`tests/requests/entities.rs`, `tests/models/entities.rs`, and the several other suites that reach `content_entities` indirectly) was re-run in full and needed no changes, since every PostgreSQL branch is unchanged from before this entry.
