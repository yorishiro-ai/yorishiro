# Contributing

## Where code goes

The layout follows a standard MVC split, with Rust's module system standing in for directories.

| Location | Holds |
|---|---|
| `src/models/` | Record shapes, input DTOs, and the queries that read and write them |
| `src/controllers/` | What a request means, and what to do about it |
| `Hooks::routes` in `src/app.rs` | The URL to controller map |
| `src/services/` | Decisions that outlive one request: auth, embedding, MCP |
| `migration/src/` | Schema versioning |
| `Hooks::seed` in `src/app.rs`, `templates/*.json` | Seed data |
| `src/tasks/` | Admin and one-off commands, via `cargo loco task` |

The paid edition mirrors models, controllers and services under `ee/crates/yorishiro-hosted/src/`, for the tables and endpoints it adds.

### A model owns a table

Its shape and its queries live in the same module.
There is no repository layer: `repositories` names a pattern, not a layer, and a directory named after it left `models` holding nothing but structs while every query sat next door.

`src/models/_entities/` is generated by `cargo loco db entities` and never hand-edited.
Business logic goes in `src/models/<table>.rs` alongside it.

If you are adding a table, add a migration under `migration/src/`, regenerate the entities, and add a module under `models/`.
If you are adding a decision that reaches for a table, put the decision in `services/` and the query in `models/`.

### What is not a model

`migration/src/`, `templates/*.json` and `db.rs` are the database's concerns, not a model's, and they stay outside `models/` on purpose.

### Where the queries are

A new table's queries belong in `models/`.
Raw SQL is for what the SeaORM entity API genuinely cannot express: JSONB containment (`data @> filter`), pgvector similarity search, and advisory locks.
Everything else uses `Entity::find()`/`ActiveModel`/`Set(...)`, on whichever connection or transaction the caller holds.

Some raw SQL outside `models/` is correct and stays:

- `src/db.rs` is connection handling, not table access: its `SET ROLE`/`RESET` statements are the pool's session lifecycle.
- `src/services/auth/authenticate.rs` reads keys as part of deciding a request's identity, which is a decision rather than a record.
  Its `last_used_at` write is part of that same decision, and deliberately runs on its own short-lived connection rather than the request transaction, which would roll it back on every read-only or rejected request.
- `src/services/embedding/sync.rs` and `src/tasks/resync_embeddings.rs` write and scan the `embedding` column, which is pgvector-typed and has no entity-API expression.
- `ee/crates/yorishiro-hosted/src/services/official_templates.rs` is a seeder, and seeders sit outside the model by the same mapping that puts `migration/src/` there.
- `ee/crates/yorishiro-hosted/src/services/tenant_auth.rs` is the auth exception's paid-edition mirror: `TenantScopedAuthenticator::authenticate` is this crate's `Authenticator` impl, and `create_tenant_api_key` is `create_api_key` with a tenant-exists check and a role-cap check folded in, both decisions rather than records.

`ee/crates/yorishiro-hosted/src/controllers/inference.rs` holds a query that belongs in `models/` and has not been moved yet.
If you are already editing it, moving the query is welcome.
If not, leave it: a move with no reason to touch the file is a diff nobody can review against a behaviour change.

### MCP is a service, not a controller

`src/services/mcp/` holds the server type (`YorishiroMcpServer`) and the per-domain `#[tool_router]` implementations, even though MCP tools are an entry point the way a controller is.
This is a deliberate exception to the table above: MCP is a seam `ee/` composes against, not route logic.
Route *mounting* is a one-line `src/controllers/mcp.rs::mount()`, called from `Hooks::after_routes`, and that one line is the part that belongs in `controllers/`.

## Tests

`tests/` is a plain Loco integration-test crate.
There is no `#[path]` include and no `autotests = false`: a file under `tests/` is compiled and run because it is there.

Request tests boot the app with `loco_rs::testing::request::request_with_create_db::<App, _, _>`.
**Every one of them must call `close_app_pools` before its closure returns**, or teardown panics even on a passing test: the app opens pools Loco's harness does not know about, and none of them close on their own.
`tests/requests/mod.rs` holds that helper and is the pattern to copy.

In `ee/`, shared test helpers are declared once, in `tests/lib.rs`, and reached with `use crate::tests::test_helpers;`.
Declaring `mod test_helpers;` in several files trips `clippy::duplicate_mod`.

## Before you push

```sh
make check          # cargo check --workspace
make clippy         # cargo clippy --workspace --all-targets -- -D warnings
make fmt-check      # cargo fmt --check
make test           # cargo test --workspace
```

`make -C <path> <target>` works from anywhere, which matters because `cargo loco task` and the CLI binary require `config/` to be the process's own working directory.

The test suite needs PostgreSQL with `vector` and `pg_trgm` installed **in `template1`**, not just in the deployment's own database: Loco's harness makes each throwaway test database with `CREATE DATABASE`, which copies `template1`.
Check it with `psql -d template1 -c '\dx'` rather than assuming.

It also needs a role that is **not** a superuser.
A superuser bypasses RLS regardless of `FORCE`, so a green run as one proves nothing about isolation.

## Prose in this repository

One sentence per line, in Markdown and in comments.
Do not hard-wrap, and do not join two clauses with a dash.

`migration/src/` is not exempt from this: `sea-orm-migration` does not checksum migration files, unlike the sqlx migrations this project used previously, so editing an applied migration is safe.
