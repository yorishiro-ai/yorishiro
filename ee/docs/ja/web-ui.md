# Web UI

[English](../web-ui.md) | **日本語**

`ee/web`はこのプロダクトのUIです。
React SPAであり、これが唯一のUIです——かつて並存していたvanilla JSのUIは廃止しました。

このSPAは`ee/web/dist`から`rust-embed`でバイナリに**組み込まれます**。
READMEが約束している「バイナリ1つ、起動すればUIが出る」を保つのはこの仕組みです。
`dist/`はビルド成果物でありコミットしないため、ビルドは`cargo build`の前に`ee/web`で`pnpm run build`を実行します——CI・リリースワークフロー・Dockerfileのいずれもそうしています。
この手順を飛ばしたチェックアウトは`embeds_a_built_spa`テストで落ちます。
`/`が空の404を返すバイナリが出来上がるより先に気付けます。

`YORISHIRO_WEB_DIR`を設定すると、組み込み済みのコピーの代わりにディスク上のディレクトリから配信します。
リクエストごとに読み直すため、バイナリを再ビルドせずUIを編集・反映できます。

ライセンスキーを要する画面は、キーが無い場合APIが返すエラーをそのまま表示します。
UI自体はgate対象ではありません。
セットアップ・ログイン・メンバー/ワークスペース管理は無償の範囲だからです。

**`ee/web`はpnpmプロジェクトです。**
lockfileは`pnpm-lock.yaml`で、pnpmのバージョンは`package.json`の`packageManager`フィールドに固定されています(CIは`pnpm/action-setup`、Dockerイメージは`corepack enable`を通じてこれを読みます)。
ここで`npm install`を実行すると`pnpm-lock.yaml`が完全に無視され、ビルド・テスト済みのものとは異なる依存ツリーが解決されてしまいます——`pnpm install`を使ってください。
`pnpm run check`はCIと同じlint/format/typecheck/buildの一連を実行します。

認証後のデータ取得・更新リクエストは、[APIリファレンス本体](../../../docs/ja/api.md)および[api.md](api.md)に記載されている、bearerキー方式のREST APIを経由します。
SPA自体はAPIが強制していない特権的なアクセス権を一切持ちません。
ログイン・サインアップ・OAuthフローは例外です——これらはまさにbearerキーを最初に取得するための手段そのものなので、キーなしで到達できる必要があります。

## ダッシュボードのパネル(`/dashboard`, `/ws/:wsId/dashboard`)

両ダッシュボードは`Card`ではなく`Panel`・`Stat`・`UsageBar`(`components/ui/Panel.tsx`)で構成します。
Grafana風の密度を出すためで、小さな大文字のタイトルバー、そのバー右端の注記(エンティティ数チャートの「mean N」)、パネル端まで使うコンテンツ領域を持ちます。
パネル下のナビゲーションタイルは読み取り値ではなくリンクであるため、引き続き`Card`を使います。

チャートはSPAが既に依存している`recharts`のままとし、色はUI全体と同じCSSカスタムプロパティから取ります。
これによりチャート専用のパレットを持たずに両テーマへ対応します。
フロー図・グラフ表示は引き続きReact Flowであり、これらのパネルが置き換えるものではありません。

`limit`を与えた`Stat`は上限への近さで色が変わります。
上限の75%未満は通常色、75%から警告色(amber)、90%以上は危険色(destructive)で、上限超過時もそのままです(`thresholdClass`。`thresholds.test.ts`で境界値を固定)。
`UsageBar`は同じ比率をバーで表示し、**上限が`null`の場合は何も描画しません**。
無制限には満たすべきバーが無く、全幅のバーは「上限到達」に見えてしまうためです。
これにより`max_workspaces`とワークスペースの`max_entities`が画面に出ます。
いずれも従来から取得はしていて未使用でした。

## スキーマバージョン切り替え(`/ws/:wsId/schema`, `/ws/:wsId/schema/io`)

このページはまずワークスペースのスキーマ名を1度だけ解決し(`workspace.schema_id`を使用、無ければ`active`ステータスのスキーマにフォールバック)、その名前の全バージョンを`GET /api/schemas`から取得します。
このエンドポイントはarchived済みを含むテナントの全バージョンを返すため、バージョン降順にソートして一覧化します。
スキーマ名の隣にあるドロップダウンで任意のバージョンを選択でき、選択すると`GET /api/schemas/{schema_id}`でそのバージョンの定義を取得します。

デフォルトではアクティブなバージョンが選択されます。
選択中のバージョンの`status`が`active`以外(実際には`archived`が典型ですが、`draft`や`deprecated`も同じ「`active`でない」条件に該当します)になると、ページは読み取り専用になります:

- 説明用の注記が表示され、「Edit Definition」ボタンは非表示になります。
- Import/Exportタブのリンクは視覚的に無効化されクリックできなくなります。
  読み取り専用バージョンで既に`/schema/io`を表示している場合、通常のインポート/エクスポート操作の代わりに説明用のカードが表示されます(非表示ではなく置き換え)。
  ワークスペースへのインポート/エクスポートは現在のアクティブなスキーマに紐づく操作であり、任意の過去バージョンには適用できないためです。
- スキーマ構造グラフ、エンティティタイプ表、リレーションタイプ表、Raw JSONは、アクティブなバージョンと同様にそのバージョンの内容で表示され続けます。

編集(「Edit Definition」による新バージョン作成)はアクティブなバージョンを表示している場合のみ可能です。
保存すると常にバージョン`N+1`が作成され、それまでのアクティブなバージョンはarchivedになります。
これは既存の`POST /api/schemas`の仕様と同じです。

## スキーマバージョンdiff表示(`/ws/:wsId/schema`)

エンティティタイプ表・リレーションタイプ表の下に「Version Diff」カードがあり、任意の2バージョン間の差分を`@pierre/diffs`によるgit diff形式で表示します。
`From`・`To`の2つのドロップダウンで比較対象を選択し、初期値は最新2バージョンであるため、カードを開いた時点で直近の変更が表示されます。
各バージョンの定義は`GET /api/schemas/{schema_id}`で個別に取得します。
`GET /api/schemas`はサマリのみを返し`definition`本体を含まないため、一覧取得だけでは差分を取れません。

比較前に両者のオブジェクトキーをソートしたうえでシリアライズします(`stableJson`)。
JSONのキー順序は意味を持たず、サーバーを往復する際に保持されないため、そのままシリアライズして比較するとキーの並び替えが変更として報告されてしまうためです。
配列の順序は位置に意味があるためソートしません。

diff表示は読み取り専用の操作であるため、archived済みバージョンでも表示されます。
バージョンが1つしか無い場合は比較対象が無い旨を表示し、選択した2バージョンのシリアライズ結果が同一の場合は空のdiffではなくその旨を表示します。

## インポート(`/ws/:wsId/schema/io`)

インポートは単一の`.jsonl`ファイルに加え、複数の`.jsonl`を含む`.zip`アーカイブを受け付けます。
どちらも同じ`POST /api/import.jsonl`エンドポイントを使用するため、行単位のバリデーションとエラー表示は共通です。
ZIPの展開はブラウザ側(`fflate`)で行い、メンバーを1件ずつ送信するため、サーバー側に専用の形式は存在しません。

メンバーは**ファイル名順**にインポートされ、対象は拡張子`.jsonl`のメンバーのみです。
ディレクトリエントリ、`__MACOSX/`のリソースフォーク、ドットファイルは除外します。
これらは実際のアーカイブに頻繁に含まれており、送信するとユーザーが意図していない内容でエラーになるためです。
スキーマを、それを参照するエンティティより先に適用するには、依存順にソートされるファイル名(`01-schemas.jsonl`、`02-entities.jsonl`)を付けます。

集計結果は全メンバーの合計です。
メンバー間でのアトミック性は保証しません。
途中のファイルが失敗した場合、それより前のメンバーは既に適用済みであるため、エラーはアーカイブ全体ではなく失敗したファイル名を示します。

## リクエストがどのワークスペースに作用するか

コンテンツ系エンドポイントはワークスペース単位であり、`X-Workspace-Id`が無ければサーバーはAPIキーに記録されたワークスペースへ解決する。
SPAはURLがキー自身のワークスペース**以外**を指しているときに限りこのヘッダを送る(キー自身のワークスペースはサインイン時に記録する)。

送らないと、2つ目のワークスペースを開いても1つ目のエンティティ・スキーマ・検索結果が2つ目のURLの下に表示され、食い違いを示すものが何も無い。
常に送るのも不可で、`/auth/login`が発行するのはワークスペーススコープのキーであり、別ワークスペースを指すヘッダは拒否されるため、本来サインインしたワークスペースへの全リクエストが失敗する。

指定ワークスペースに到達できないキーの場合は、解決手段(そのワークスペースを選んで再サインイン)を示す1文を表示する。
APIの原文はヘッダ名を告げるだけで次の行動が分からないため。

## 一覧でのエンティティ名

エンティティの表示名は `title` / `name` / `label`のうち最初に見つかった文字列とし、無ければid接頭辞にフォールバックする(`entityLabel`)。
idは時系列順のため、同一セッションで作成した行はid接頭辞が全て同じに見える。
エンティティ一覧・検索結果・グラフの選択リストはいずれもこれが無いと「同じ行が並んでいる」ようにしか見えない。

検索結果には類似度も表示する。
値は `1 - distance`とする。
並び順はdistanceで決まるため、表示しないとランキングの根拠が読めない。
検索結果として読者が期待する向き(高いほど一致)に合わせている。

## ディープリンク

全ルートはURLから直接到達できる(フルリロードを含む)。
`TenantScope`はテナント階層のルートが描画されるときに記憶中のワークスペースを忘れるが、この処理は**画面遷移を伴ってはならない**。
`/dashboard`へ遷移していた頃は、`/marketplace`・`/schemas/:id`・`/schemas/templates/:id`をフルリロードすると描画前にダッシュボードへ飛ばされていた。
アプリ内のクリック操作では子ルートだけが変わる場合に当該effectが再実行されないため、この不具合は表面化しなかった。

そのため `useWorkspace`は2つを提供する。
`clearWorkspace`は遷移せずに忘れるだけ、`leaveWorkspace`は忘れた上でダッシュボードへ戻る(サイドバーの「Back」の意味)。

## テーマとカラートークン

両テーマは `web/src/index.css`のCSSカスタムプロパティで駆動する。
`@theme`ブロックがライトを定義し、`.dark`が変化するものだけを上書きする。
`useTheme`が `<html>`の `dark`クラスを切り替え、選択を `yorishiro_theme`に保存する。
未保存の場合は `prefers-color-scheme`に従う。

テキストを持つトークンは、WCAG AAのコントラスト比(本文4.5:1、大きな文字3:1)を**そのテキストが載りうる最も暗い面に対して**満たすよう選ぶ。
ページ背景に対してだけではない。
二次テキストはページと同じ頻度で `--color-muted`の上に載るため、`--color-muted-foreground`は `--color-muted`に対して測る。

2つのトークンは意図的に両テーマで共有しない。
いずれもコントラストが理由である。

| トークン | ライト | ダーク | 理由 |
|---|---|---|---|
| `--color-muted-foreground` | `#66666e` | `#a1a1aa` | 二次テキスト。1つの値では両立しない。zinc-500 はライトのページ上で4.6だが、`#27272a` の上では3.1まで落ちる |
| `--color-link` | `#4f46e5` | `#8b93f8` | primary を**テキストとして**使う場合。`--color-primary` と分けるのは両者が逆方向を向くため。白いボタンラベルを載せられるほど暗い塗りは、暗い面の上でリンクとして読むには暗すぎる |

リンクなど primary 色のテキストには `text-link`を使う。
`--color-primary`はボタン・アクセントの*塗り*であり、常に `--color-primary-foreground`と対で使う。

アイコンのみのコントロール(テーマ切り替え、サインアウト、グラフの再読み込み)には `aria-label`を付ける。
`title`だけではスクリーンリーダーに名前が伝わらない。

次の2つの配色はトークンではなくテーマごとに選ぶ。
グラフのキャンバスへインラインSVGのstyleとして描画され、CSSカスタムプロパティを解決できないためである。

- **リレーションのエッジ配色**(`relationPalette`) — 6色。
  ダークでは明るく、ライトでは暗くする。
  固定パレットでは両立しない。
  emerald はライトのキャンバス上で2.4、indigo はダークで4.0となり、これらの色相でライト・ダーク双方の4.5を満たす値は存在しない
- **フィールド型の配色**(`fieldTypeColor`) — カード背景でも同じ問題が起きるため、Tailwind の `dark:`バリアントで解決する(ライトは `-700`、ダークは `-400`)

どちらかを描画するコンポーネントは `useIsDarkMode`から `isDark`を受け取る。
このフックは `<html>`のクラスを監視するため、テーマの設定経路によらず正しい値を返す。
