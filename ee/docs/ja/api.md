# 有償機能APIリファレンス

[English](../api.md) | **日本語**

このページのエンドポイントは`ee/`が追加するものです。
それ以外(スキーマ・エンティティ・検索・認証・メンバー/ワークスペース管理など、サーバが提供する残り全部)は[APIリファレンス本体](../../../docs/ja/api.md)にあります。

これらのエンドポイントは、サーバの他の部分と同じデータベース内にある`identity.tenants`/`identity.tenant_memberships`/`identity.users`を直接読み書きします。

ほとんどはライセンスキーが必要です。
対象と、キーが無い場合に何を返すかは[configuration.md](configuration.md#ライセンスキー)を参照してください。

## OpenAPI

このプロセスは OpenAPI ドキュメントを**2つ**配信します。
それぞれがルータの片側について正典です:

| ドキュメント | 対象 |
|---|---|
| `/api-docs/openapi.json` | コアAPI: スキーマ・エンティティ・リレーション・検索・認証・ワークスペース |
| `/api-docs/hosted-openapi.json` | このページに記載のエンドポイント |

統合せず分離しているのは、前者を`yorishiro-server`が `build_app`の内部で自身の crate 内非公開(`pub(crate)`)な `ApiDoc`から構築・マウントしており、`ee/`からは参照も拡張もできないためです。
加えて `axum::Router::merge`は同一パスの重複を許しません。
どちらも認証不要で、APIキーなしに取得できます。

どちらも生のJSONです。
`/docs`に Swagger UI も登録されていますが、現状 `/docs`が `/docs/`にリダイレクトした先で 404 になります(UIのアセットが配信されないため)。
UIに頼らず、JSONを直接取得してください。

## コアルートの上書き

`ee/`のルートを**先に**マッチさせ、コアのルータをその背後のフォールバックに置きます。

```rust
hosted_router.merge(oauth_login_router).fallback_service(base_app)
```

横に並べてmergeするのではありません。
`axum::Router::merge`はパス重複でpanicするため、merge構成では「コアが提供していないパスの**追加**」しかできません。
この構成では**置き換え**もできます。
コアが定義しているエンドポイントを、コアに何も知らせることなく、有償機能固有の挙動が引き取れます。

解決順序は、`ee/`のルート → コアのルート → 静的アセットフォールバックです。
未マッチのパスはSPAの`index.html`に到達し、これによってSPAがクライアント側ルーティングを担えます。

ルートを追加する際の注意点は2つです。

- **パスを上書きすると、そのパスの全メソッドを上書きします。**
  パスは一致するがメソッドが一致しないリクエストは、このルータの`405`を受け取り、コアの当該メソッドのハンドラには到達しません。
  そのパスに必要な全メソッドを定義するか、パスごと触らないかのどちらかにしてください。
- レイヤは境界を越えません。
  各サブルータは`apply_observability_layers`/`apply_body_limit_layer`を自前で持ちます。

単一プロセスが両方を提供するため、上書きは最終的なものです。
コア側のそのルートがまだ到達可能な別プロセスは存在しません。

## `POST /hosted/stripe/webhook`

Stripeのサブスクリプションイベントを受信します。
`Stripe-Signature`ヘッダー(`YORISHIRO_STRIPE_WEBHOOK_SECRET`を鍵とした`{timestamp}.{body}`のHMAC-SHA256、タイムスタンプが現在時刻から前後どちらの方向にも5分以上ずれている場合は拒否)を検証してから処理します。

| レスポンス | 発生条件 |
|---|---|
| `501 Not Implemented` | `YORISHIRO_STRIPE_WEBHOOK_SECRET`が未設定。このデプロイでStripeが未設定 |
| `400 Bad Request` | `Stripe-Signature`ヘッダーが欠落/不正、またはJSONボディが不正な形式 |
| `200 OK` | イベントを検証・適用した(またはこのデプロイが処理しないイベント種別だった) |
| `500 Internal Server Error` | イベント自体は有効だが適用に失敗(DBエラー等) |

処理対象のイベント種別:

| イベント | 効果 |
|---|---|
| `checkout.session.completed` | チェックアウトセッションの`client_reference_id`(作成時にテナントのUUIDが設定されている想定)が指すテナントに、StripeカスタマーIDを紐付ける |
| `customer.subscription.created` / `customer.subscription.updated` | 紐付け済みのStripeカスタマーIDからテナントを解決し、サブスクリプションの価格IDを`YORISHIRO_STRIPE_PRICE_PRO`/`YORISHIRO_STRIPE_PRICE_TEAM`経由でプランにマッピングし、そのプランの`max_workspaces`上限を適用する |
| `customer.subscription.deleted` | テナントを`free`プランの上限にリセットする |

上記以外のイベント種別は副作用なしで`200 OK`を返します(Stripe側の記録用にのみ使われるinvoiceイベントなど)。

適用済みの各イベントのStripeイベントIDは`identity.stripe_processed_events`に記録され、既に記録済みのイベントIDが再度届いた場合は`200 OK`を返して受理はする(Stripe側のリトライを止めるため)ものの、再適用はしません。
`customer.subscription.*`系の3イベント種別に限っては、Stripeが配信順序を保証しないため、同一Stripeカスタマーに対して既に適用済みの最新の`customer.subscription.*`イベントより`created`タイムスタンプが古い配信も同様に受理はしつつ再適用しません。
`checkout.session.completed`はこの顧客単位の順序チェックの対象外です。
これは1回限りの紐付けイベントでサブスクリプションの流れとは順序的な関係を持たず、同じ購入に対する`customer.subscription.created`(より古い`created`を持ちうる)より先にStripeから配信されることがあるためです。

## `GET /hosted/tenant/overview`

管理ダッシュボードのトップ画面が必要とする唯一の読み取りです。
プラン・ワークスペース上限・使用量カウンタ・メンバー一覧を1回のリクエストで取得します。

```console
$ curl localhost:8080/hosted/tenant/overview -H "Authorization: Bearer $YORISHIRO_KEY"
```

`/auth/login`が発行するのと同じ形式のbearer APIキーが必要です(欠落・不正なbearerトークンは`401 Unauthorized`)。
呼び出し元のテナントmembership roleが`owner`または`admin`であるアクセスのみ許可し、`member`roleのキーはキー自身の`ApiKeyScope`に関わらず`403 Forbidden`になります。
課金/使用量データはキーが持つコンテンツscopeとは独立したテナント管理者向けの関心事だからです。

レスポンス形式:

```json
{
  "tenant_id": "...",
  "plan": "pro",
  "max_workspaces": 5,
  "usage": {
    "tenant_id": "...",
    "workspace_count": 2,
    "member_count": 4,
    "entity_count": 1230
  },
  "members": [
    { "user_id": "...", "email": "...", "display_name": null, "role": "owner" }
  ]
}
```

`plan`はStripeサブスクリプションイベントが一度も適用されていなければ`null`です。
一度もサブスクライブしていないテナントにはプランも上限もありません。
`usage`はテナントが持つ全ワークスペースを横断して集計されます。

## テンプレートマーケットプレイス

テンプレートをテナント間で共有する。
`identity.templates`は既に `visibility`(`tenant` | `community`)と `fork_of`を持っており、マーケットプレイスはその上に「共有されたテンプレートを安全に使うための情報」(公開済みバージョンと、他テナントの評価)を載せる。

**本版が提供する。**
テンプレートをテナント間で配布することは、どのテーブルが保持していようとエンタープライズの機能であるため。

| エンドポイント | スコープ | 用途 |
|---|---|---|
| `GET /api/marketplace` | 有効なAPIキー | 全テナント横断の公開テンプレート一覧。最新stableバージョンとレビュー集計を含む |
| `GET /api/marketplace/{id}/versions` | 有効なAPIキー | 公開済みバージョン(新しい順)。draftは自テナント所有のテンプレートのみ含む |
| `POST /api/marketplace/{id}/versions` | 有効なAPIキー | 自テナントのテンプレートの次バージョンを公開(`definition`、任意の`changelog`、`status`は`draft`/`pre`/`stable`) |
| `GET /api/marketplace/{id}/reviews` | 有効なAPIキー | 閲覧できるテンプレートのレビュー一覧 |
| `POST /api/marketplace/{id}/reviews` | 有効なAPIキー | 自テナントのレビューを投稿・更新(`rating` 1-5、任意の`comment`) |
| `POST /api/marketplace/{id}/fork?version=N` | 有効なAPIキー | 公開済みバージョンを自テナントのライブラリへコピー。`version`省略時は最新の`stable` |
| `PUT /api/marketplace/{id}/visibility` | 有効なAPIキー | 自テナントのテンプレートを公開する/取り下げる |

バージョン番号はサーバが採番し、テンプレートごとに増加する。
クライアントに選ばせると、他テナントが履歴として読む連番に欠番や衝突が生じる。

**draftは所有テナントにのみ見え**、forkもできず、非draftが1つも公開されるまでそのテンプレートを一覧から除外する。
インストールで404になるlistingは、短い一覧より悪い。
forkした複製は自ライブラリに**非公開**で入る。
他人の成果を自分の名前で再公開することは、既定ではなく決定であるべきだから。

自テナントが所有しないテンプレートへの操作は`403`ではなく`404`を返す。
操作できない呼び出し元が、その差分から存在を確認できてはならない。

forkはテンプレートであってスキーマではない。
`POST /api/schemas`にそのUUIDを`template_id`として渡して適用する。
組み込みテンプレートIDの適用と同じ手順。

### 公式listing

組み込みテンプレートもここに公開される。
公開は `yorishiro-server seed-official-templates`が行う。
これらは通常のlistingであり、他と同様にforkもレビューもできる。
author は `Yorishiro`。

公開元は**メンバーもワークスペースも持たない**テナント行である。
`identity.templates.tenant_id`は `NOT NULL`であり、マーケットプレイスは所有権をこの列で判定するため、公式listingにも所有者が必要になる。
ログインの経路となるメンバーシップが存在しないため、このテナントにログインすることは誰にもできない。

このコマンドは冪等で、毎デプロイ実行される前提。
同一定義で公開済みのテンプレートは放置され、新リリースで定義が変わったものは、既にインストール済みのバージョンを書き換えるのではなく**新バージョンとして公開**される。

## 出自テンプレートへの追従

テンプレートから作られたスキーマは、その出自を記録する。
複製後は双方が動きうるため、この3エンドポイントが「テンプレート側の変更を取り込む/取り込まない」を workspace が決める経路になる。

**本版が提供する**。
マーケットプレイスと同じ理由で、テンプレートの変更を複製先へ配布することはテンプレート配布だからである。
**作成**は配布ではなく、コミュニティ版に属する: `POST /api/schemas`の `template_id`、`GET /api/templates`、`origin_*`列である。

| エンドポイント | スコープ | 用途 |
|---|---|---|
| `GET /api/schemas/upstream-changes` | read | 出自テンプレートが複製後に編集されたスキーマを返す。**報告のみ** |
| `GET /api/schemas/{schema_id}/merge-preview` | read | 追従した場合の影響。差異のある各フィールドを`auto_add`／`auto_update`／`keep_local`／`conflict`に分類する。**書き込みは行わない** |
| `POST /api/schemas/{schema_id}/merge` | schema | マージ結果をスキーマの次バージョンとして書き込む。衝突が1件でもあれば拒否する |

比較するのは2つではなく**3つの定義**である。
複製時点のテンプレート、現在のテンプレート、そしてこの workspace 自身のもの。
2つだけでは「上流の追加」と「ローカルの追加」がどちらも「向こうにあってこちらに無い」となって区別できず、追従が workspace 独自のフィールドを黙って削除してしまう。

**衝突は人間が判断する事柄である。**
`merge`は片方を選ばずに拒否する。
どちらを選んでも、負けた定義で書かれたエンティティが検証を通らなくなるため。
スキーマを編集して解消してから再度マージする。

テンプレートに追従していないスキーマ、およびマージ基底が記録される前に複製されたスキーマは、推測せずに拒否する。
欠けている基底の代わりに現在のテンプレートを使うと、ローカルの追加がすべて衝突として読まれてしまう。

これらのエンドポイントは**両方の種類のキー**を受け付ける。
ワークスペーススコープのキーは自身のワークスペースを、テナントスコープのキーは `X-Workspace-Id`でリクエストごとに指定する。
コミュニティ版にあった頃は前者しか存在しなかった。

**MCPツールは提供しない。**
`list_upstream_changes`／`merge_preview`／`merge_apply`はコミュニティ版にあった頃はMCPツールでもあったが、`/mcp`はコミュニティ版が埋め込むサーフェスであり、本版から追加することはできない。
本版ではRESTのみ。

## 欠損値の推測

`fill-defaults`がスキーマ自身の述べる値を書くのに対し、こちらはエンティティが既に持つ内容からモデルに値を提案させる。
対象は「欠けていて、かつ妥当な既定値を持たない」フィールドである。

**本版**が提供する。
**決めるのはサーバが外部へchat completionを呼ぶという性質そのもの**であって、誰が費用を負担するかではない。
BYOキー方式にしても、費用の所在が変わるだけでこの判定は変わらない。
埋め込みプロバイダはこれと同じではないので残っている: `/embeddings`はchat completionではなく、ローカルONNXプロバイダはネットワーク呼び出しを持たない。

| エンドポイント | スコープ | 内容 |
|---|---|---|
| `PUT /api/workspace/llm-key` | schema | ワークスペース自身のエンドポイント・モデル・キーを保存 |
| `GET /api/workspace/llm-key` | read | エンドポイントとモデルを返す。**キーは返さない**(マスク済みでも返さない) |
| `DELETE /api/workspace/llm-key` | schema | 削除。以後 `infer-fill` は再び拒否する |
| `POST /api/schemas/active/{name}/infer-fill` | schema | 提案を保存し `job_id` を返す。エンティティは不変 |
| `GET /api/migration-jobs/{job_id}/proposals` | read | モデルの提案一覧 |
| `POST /api/migration-jobs/{job_id}/confirm` | schema | 同一 `job_id` でスナップショットを取ってから適用 |

**推論コストはデプロイメントが負担しない。**
ワークスペースが自身の資格情報を設定する。
OpenAI互換のchat-completionsエンドポイントであれば何でもよく、Ollama・LM Studio を含む。

**この「何でも」は文字どおりで、運用者が判断すべき露出である。**
`base_url`は与えられたまま保存され、宛先は制限されない。
したがって `schema`スコープのキーを持つ呼び出し元は、サーバが到達できる任意のホスト(デプロイメント自身のネットワーク上のサービスを含む)を指定でき、そのリクエストにはエンティティのデータとワークスペースのbearerトークンが載る。
運用者とテナントが同一であるセルフホストではこれは機能の意図どおりだが、マルチテナントではテナントがサーバを探索の踏み台にでき、応答は本人が読める提案として保存される。
**制限は意図的に未実装である**：許可リスト・egressプロキシ・私有アドレス範囲の拒否のいずれを採るかは運用者の判断であり、既定を誤ると上記のlocalhostエンドポイントが使えなくなる。
狭い2点のみ強制している: `base_url`は `http://`または `https://`であること、そしてリダイレクトは追わず拒否すること(307がボディとヘッダを、誰も設定していないホストへ再送するのを防ぐ)。

**後から制限を入れる場合は、設定時のホスト名ではなくリクエスト時の解決済みIPを検証すること。**
`PUT`の時点で公開アドレスへ解決した名前が、リクエストが出る頃には`127.0.0.1`へ解決しうる。
保存時のチェックは、実際に使われるのとは別の解決結果を検証していることになる。
reqwest での実装点はカスタムDNSリゾルバであり、保存時のチェックは「人が早く気づくためのエラーメッセージ」としてのみ残す。

キー未設定のワークスペースは既定値へフォールバックせず **422** を返す。
推測を要求した呼び出し元が `default`値を受け取ると、推測が行われなかったことを判別できないためである。

**提案は書き込みではない。**
確定は `POST /api/migration-jobs/{job_id}/undo`が巻き戻すのと同じ機構でスナップショットを取るため、確定済みのバッチも `fill-defaults`と同様に戻せる。
スキーマが拒否する提案はバッチ全体を失敗させず `skipped`に数える。
**同じjobは1度しか確定できない**。
適用時に提案を削除するため、undo後に再確定してundoが戻した内容へ同じ推測を書き戻すことはできない。

`identity.workspace_llm_keys`はキーを平文で保持し、**`yorishiro_app`にはGRANTを与えない**：リポジトリはマイグレーションロールのプール経由で到達するため、リクエスト接続で届いたクエリはRLSポリシーの正しさに依存せず権限チェックで落ちる。
保存時暗号化はボリュームまたはマネージドDBの層が担う。
守る対象のデータと同じホストに置かれた鍵は、どのみちダンプと同時に流出する。

**MCPツールは提供しない。**
`/mcp`はコミュニティ版が埋め込むサーフェスであり、本版から追加することはできない。
この6本はRESTのみ。

## テナントスコープAPIキー

コミュニティ版のAPIキーは1つのワークスペースに紐づくため、複数ワークスペースをまたぐクライアントはワークスペースごとにキーを保持して切り替える必要があります。
このエディションで発行するキーは**テナント**に紐づけることができ、対象ワークスペースを`X-Workspace-Id`ヘッダでリクエストごとに指定します。

```console
# 発行(キー発行のRESTエンドポイントは存在しません)
$ yorishiro-server create-tenant-api-key <tenant-id> write

# 各リクエストで対象ワークスペースを指定する
$ curl localhost:8080/api/entities -H "Authorization: Bearer $YORISHIRO_KEY" \
    -H "X-Workspace-Id: <workspace-id>"
```

実現方法は`yorishiro_core::services::auth::Authenticator`(コミュニティ版が持つ「キー解決の差し替え口」)の実装を差し込むことです。
これによりヘッダは**全ての**認証経路で有効になります。
RESTもMCPも同様で、「参照することを覚えていたルート」だけではありません。

| キー | `X-Workspace-Id` | 結果 |
|---|---|---|
| ワークスペーススコープ | 省略 | キー自身のワークスペースに対して実行 |
| ワークスペーススコープ | キー自身のワークスペースと一致 | 省略時と同じ |
| ワークスペーススコープ | 別のワークスペースを指定 | `422`。そのキーでは実行できず、黙ってキー自身のワークスペースで実行するとクライアントが指定していない場所に書き込むことになるため |
| テナントスコープ | 省略 | `401`。フォールバック先のワークスペースが無いため |
| テナントスコープ | 自テナント配下のワークスペース | そのワークスペースに対して実行 |
| テナントスコープ | 他テナントのワークスペース | `401`。未知のキーと区別がつかない |
| いずれも | UUIDでない値 | `422` |

**テナントスコープのキーが自テナントの外に到達することはありません。**
`identity.authenticate_api_key`の2引数版は、指定されたワークスペースがそのキーのテナント配下にある場合にのみ解決し、この判定は認証時、いずれの行を読むよりも前に行われます。

コミュニティ版の1引数版`authenticate_api_key(bytea)`はそのまま残します。
Postgresは引数個数でオーバーロードするため、これは追加であって置き換えではありません。
1引数版は`identity.workspaces`をINNER JOINするため、同じDBを読むコミュニティ版のプロセスはテナントスコープのキーを誤解決せず拒否します。
どのワークスペースを指しているか知る手段が無いプロセスとして、これが正しい応答です。

scopeの扱いはワークスペーススコープのキーと同一です(`read` < `write` < `schema`。紐づくユーザーのテナントroleが上限)。
適用範囲がテナント配下の全ワークスペースになるだけです。
単一ワークスペースしか扱わないクライアントにはワークスペーススコープのキーを推奨します。
漏洩時の到達範囲が狭いためです。

## OAuth2/OIDCログイン

コミュニティ版の`POST /auth/login`(メール/パスワード)に加えて、YorishiroのAPIキーを取得するためのオプションの認証方式です。
デフォルトでは無効で、有効化に必要な環境変数は[configuration.md](configuration.md#oauth2oidcログイン)を参照してください。
OAuth未設定時、`GET /auth/oauth/authorize`と`GET /auth/oauth/callback`はどちらもJSONエラーボディ付きの`404 Not Found`を返します。
ただしこれは必ずしもタイプミスしたURLへのリクエストと同じレスポンスとは限りません。
Web UIが配信されている場合、**拡張子を持たない**未マッチのパスは`404`ではなくWeb UIの`index.html`にフォールバックします(`200 OK`)が、拡張子を持つパス(例: `/foo.js`)は依然として実際の`404`になります。
`GET /auth/oauth/status`は例外で、常に`200`を返し、Web UIのログインページが「SSOでサインイン」ボタンを表示するかどうかの判定に使います。

IPベースのレート制限(上限に達すると`429`。`YORISHIRO_AUTH_RATE_LIMIT_MAX`/`YORISHIRO_AUTH_RATE_LIMIT_WINDOW_SECS`。詳細は[設定リファレンス本体](../../../docs/ja/configuration.md)参照)は、それを必要とする各サブルータ内でルート単位に適用されているのであってグローバルではありません。
`axum::Router::merge`は`.layer()`をmerge先へ引き継がないため、あるルートがレート制限の対象になるかどうかは、そのルートが実際に定義されているサブルータがmerge前にレイヤーを適用しているかどうかで決まります。
`yorishiro-server`の`main`は`GET /auth/oauth/authorize`/`GET /auth/oauth/callback`に明示的にこれを適用しており、コミュニティ版自身の`POST /auth/login`/`POST /auth/signup`/`GET /setup/status`/`POST /setup`と**同一のリミッターインスタンス**(つまり同一のIP単位クォータ)を共有します。
片方でクォータを使い切った攻撃者が、もう片方に切り替えても新しい枠を得ることはできません。
`/authorize`自体はAPIキーを一切発行せず、プロバイダへのリダイレクトとCSRF Cookieの設定のみを行います。
`GET /auth/oauth/callback`が、(下記の)検証を経た上で呼び出し元指定の入力(認可コード)からYorishiro APIキーを発行しうる唯一のルートであり、まさにそれゆえログイン試行と同様にレート制限の対象となっています。
`GET /auth/oauth/status`は意図的にレート制限の対象**外**です:秘密情報を一切返さず、Web UIのログインページが読み込みのたびに呼び出すためです。

### `GET /auth/oauth/status`

```json
{ "enabled": true }
```

### `GET /auth/oauth/authorize`

IDプロバイダの認可エンドポイント(`YORISHIRO_OAUTH_ISSUER_URL`の`.well-known/openid-configuration`から発見)に`302`リダイレクトします。
署名された`state`とPKCE(`S256`)チャレンジが付与されます。
このリクエストとコールバック間でサーバー側に状態を保持しません。
PKCEベリファイアは署名された`state`値自体に含まれるため、ロードバランス環境で2つのリクエストが同じプロセスに到達する必要はありません。

同時に`ysr_oauth_csrf`Cookie(`HttpOnly`、`YORISHIRO_OAUTH_REDIRECT_URI`が`https://`の場合のみ`Secure`、`SameSite=Lax`、パスは`/auth/oauth/callback`に限定、有効期限は`state`と同じ10分)を発行します。
値はブラウザごとのランダムな値で、そのハッシュが`state`に埋め込まれます。
これにより、コールバック側は「このサーバーが発行した`state`」と「そのstateを実際に発行されたブラウザが提示しているstate」を区別できます。
署名だけでは前者しか証明できません。
このCookieがなければ、攻撃者が自分自身のログインで取得した`code`/`state`のペアを被害者に踏ませることで、被害者のブラウザに攻撃者のアカウントでログインを完了させてしまう可能性があります。

### `GET /auth/oauth/callback`

IDプロバイダのリダイレクト先(`redirect_uri`)。
まず`state`の署名と有効期限を検証し、続いてその中に埋め込まれたハッシュを`ysr_oauth_csrf`Cookie(上記参照)と照合します。
Cookieが欠落しているか一致しない場合は、IDプロバイダへのリクエストを送る前に、不正な`state`と同様に拒否されます。
このCookieはこのエンドポイントのどのレスポンスでも必ずクリアされるため、2回のコールバック試行にまたがって再利用されることはありません。
これを通過すると、認可`code`をトークンに交換し、IDトークンの署名(プロバイダのJWKSを使用)と標準クレーム(`iss`、`aud`、`exp`)を検証してから:

1. 既存のYorishiroユーザーを`(provider, subject_id)`(IDトークンの`sub`クレーム。`email`ではなく`sub`を使うのは、プロバイダが安定性と一意性を保証するのは`sub`だけだから)で検索。
   この検索はIDトークンの`email_verified`クレームが`true`であることを要求しません。
   メール未検証でも自動プロビジョニングは進みます(警告ログは出ますがログイン自体は成功します)。
   メールアドレスを検証しないIDプロバイダを使う場合、なりすまし防止の責任はこのサーバーではなくプロバイダ側のアカウント作成フローが負っていることになります。
2. 初回ログイン時は、新規ユーザー(IDトークンの`email`クレームをキーに)を自動作成し、メールのローカルパートを名前としたテナント、組み込みの`general-notes`テンプレートからスキーマ、そのスキーマに紐づくデフォルトワークスペース(自動プロビジョニングされたテナントはまだStripeの契約を持たないため、Freeプランのエンティティ上限が適用される)を自動作成し、`member`ロールのメンバーシップを設定。
   プロバイダが`email`クレームを返さない場合は`422 Unprocessable Entity`を直接JSONエラーレスポンスとして返す(下記のエラーリダイレクトは経由しない)。
   既に別プロバイダ/subjectで登録済みの`email`だった場合も同様に`409 Conflict`を直接JSONエラーレスポンスとして返す。
   ユーザー行とそのテナントメンバーシップは同一トランザクション内で書き込まれるため、両者の間でリクエストが中断した場合(接続断やプロセスクラッシュ)は両方ともロールバックされ、テナントに属さない到達不能なユーザーが残ることはありません。
   同じ試行の中でそれより前に作成されたテナント/スキーマ/ワークスペースはこのトランザクションに含まれないため、クラッシュ後も残存する可能性があります。
   「テナントが一度でも参加されたか」を参照する処理はどこにもないため無害ですが、リトライで保証されるのは孤立した*ユーザー*が残らないことだけであり、完全にクリーンな状態に戻るとは限りません。
3. 再ログイン時は、既存アカウントのテナントmembershipを再チェックします。
   どのテナントのメンバーでもなくなっている、またはデフォルトワークスペースを所有するテナントのメンバーでなくなっているアカウントは、直接JSONエラーレスポンスとして`403 Forbidden`を返します。
4. `POST /auth/login`と同じ方法でYorishiro APIキーを発行(`create_api_key`を使用、スコープはアカウントのメンバーシップロールから導出)。
5. `/#api_key=<key>`に`302`リダイレクト。
   Web UIのルーターがフラグメントからキーを読み取り、保存して`#/dashboard`に遷移。
   フラグメント(サーバーには送信されない)を使うのは、キーがアクセスログや`Referer`ヘッダーに表示されないようにするため。

`/#/login?error=oauth_failed`にリダイレクトされる(JSONエラーボディではなく)のは次の2パターンのみです。
この時点での呼び出し元はリダイレクト途中のブラウザであり、APIクライアントではないためです: IDプロバイダのリダイレクトが`error=...`を含む場合、およびコールバックリクエストに`code`または`state`が欠落している場合。
それ以降の失敗は、他のAPIエラーと同様に通常のJSONエラー形式でそれぞれ固有のステータスコードを返します: `state`/CSRF/トークン/IDトークンの失敗は`401`、`email`クレーム欠落は`422`、再ログイン時のテナントmembership不整合(上記3)は`403`、`email`重複は`409`、IDプロバイダとの通信(discoveryドキュメント/JWKS取得)失敗やper-identityプロビジョニングロックの取得タイムアウト(約2秒)といった予期しない失敗は`500`。
レート制限(上記参照)を超過したリクエストはここまで到達すらせず、CSRF/state検証すら実行される前に、`POST /auth/login`と同様JSONボディなしの`429`を返します。

このドキュメントに記載の全ルートで、リクエストボディは2MBに制限されています。
`axum::Router::merge`は`.layer()`をどちらの側にも引き継がないため、`yorishiro-server`の`main`は(上記のレート制限と同様に)`ee/`自身のサブルータへ`apply_body_limit_layer`を明示的に適用しています。
このレイヤーがなくても、`axum`の`Bytes`/`Json`/`String`エクストラクタ自体が組み込みの2MBデフォルトにフォールバックします。
明示的なレイヤーは、それらのエクストラクタを使わず生の`Request`/ストリーミングボディを読むような将来のハンドラも追加でカバーします。

```console
$ curl -i localhost:8080/auth/oauth/authorize
HTTP/1.1 302 Found
location: https://accounts.google.com/o/oauth2/v2/auth?response_type=code&client_id=...
```
