# エンタープライズ設定

[English](../../../docs/en/configuration.md) | **日本語**

ライセンスキーを必要とする追加設定。

## ワークスペースごとの埋め込みプロバイダ

各ワークスペースごとに埋め込みエンドポイントを割り当てられます。`PUT /api/workspace/embedding-key` で個別の設定が可能です。

| フィールド | 説明 |
|---|---|
| `base_url` | 埋め込みエンドポイントの URL |
| `model` | モデル名 |
| `api_key` | API キー（GET で取得されることはない） |
| `dimensions` | モデルが生成するベクトルの次元数 |
| `send_dimensions_param` | リクエストに dimensions を含めるか（既定：`false`） |

## OAuth2/OIDC ログイン

OAuth2/OIDC ログインは、プロバイダの discovery document の取得、authorization code の交換、JWKS の取得を、OAuth 専用の非公開 transport seam 経由で実行します。
本番実装は `reqwest` クライアント、10 秒のタイムアウト、HTTPS または loopback に限定する URL 検証、リダイレクト制限、レスポンス解析、認証情報の redaction を保持します。
テストでは、認証、callback、PKCE、state token、cookie、ユーザープロビジョニングの動作を変えずに、3 つのプロバイダ操作だけを差し替えられます。
Loco にはアプリケーション構成とキューの拡張点はありますが、このプロバイダ固有の外向き transport の拡張点はありません。そのため、汎用 HTTP サービスを追加せず、既存の OAuth service 内で seam を構成します。

## 非同期 infer-fill

`PUT /api/workspace/llm-key` でワークスペースの LLM キーを設定してから、`POST /api/schemas/active/{name}/infer-fill` で fill を開始します。
レスポンスには永続化された `job_id` と初期状態 `queued` が含まれます。
読み取り権限を持つキーで `GET /api/inference-jobs/{job_id}` を呼び出し、状態が `completed` または `failed` になるまでポーリングします。
ジョブの状態、提案件数、適用件数、スキップ件数、シリアライズされたエラーメッセージを保存するため、サーバー再起動後もポーリングできます。
infer-fill はモデルの回答を `pending` の提案として保存し、推測値をエンティティへ直接書き込みません。
`GET /api/inference-jobs/{job_id}/proposals` で提案を一覧し、`POST /api/inference-jobs/{job_id}/confirm`、`/reject`、`/discard` で明示的に確定、拒否、破棄します。
確定時は対象スキーマに対して結合後のエンティティを検証し、確定した書き込みを `POST /api/migration-jobs/{job_id}/undo` 用にスナップショットします。古くなった提案や不正な提案はエンティティを変更せずにその状態へ遷移します。
同じジョブ、エンティティ、スキーマバージョン、入力フィールドの組み合わせに対する提案配送は冪等です。
提案の一覧には read スコープ、提案操作には workspace の schema スコープが必要です。
ワークスペースキーはジョブ、提案レスポンス、ログに含まれず、キー未設定の場合はジョブ作成前にリクエストを拒否します。
提案の確定、拒否、破棄は親ジョブが `completed` になった後だけ実行できます。
ジョブが `failed` になった場合、保留中の提案は自動的に `discarded` へ遷移し、確定できません。
`completed` の提案は、明示的に確定、拒否、破棄されるまで確認できます。現在、自動的な保持期間削除はありません。
infer-fill ジョブは現在、有効期限とキャンセルをサポートしていません。そのため、これらの状態を API で受け付けたりデータベースへ保存したりしません。
ジョブを claim できるのは状態が `queued` の間だけです。
ワーカーが claim 後にクラッシュした場合、元のワーカーがまだ実行中の可能性があるため、二重推論を避ける目的で永続化された状態は `running` のまま自動再試行されません。
`running` のジョブを再試行する場合は、運用手順で元の実行状態を確認してから対応してください。
ジョブレコードは、将来の保持期間ポリシーが導入されるまで保持されます。

OpenAI 互換の chat-completions 呼び出しは、推論クライアント内の非公開 transport seam の内側に置いています。
本番実装は設定済みの `reqwest` クライアントを使い、テストでは infer-fill の動作を変えずにネットワークだけを差し替えられます。
Loco にはアプリケーション構成とキューの拡張点はありますが、このプロバイダ固有の外向き transport に対応する拡張点はないため、Loco の拡張は使っていません。

## ワークスペースごとのワーカークラス

`PUT /api/workspace/worker-class` でワークスペースのバックグラウンドジョブを計算リソースに割り当てられます。

| フィールド | 説明 |
|---|---|
| `worker_class` | `tenant_private`、`official`、または `shared` |

## 計算ポリシーの基盤

このリリースでは、プランから導くポリシーの基本関数を定義してテストしていますが、本番のキュー実行には接続していません。
Loco Queue にはプロバイダに依存しない需要観測 API がなく、現在の計算経路にも実際のコストの情報源がありません。
そのため、このリリースはキューの優先度や SLA 目標の適用、Official バーストの自動ルーティング、計算の自動課金を行いません。

| プラン | 優先度 | キュー開始目標 | Official 基本上限 | バースト上限 |
|---|---|---:|---:|---:|
| Free | low | ベストエフォート | 1 | 2 |
| Pro | normal | 60 秒 | 4 | 6 |
| Team | high | 15 秒 | 8 | 12 |

純粋なバースト判定関数は、Official の観測需要が基本上限を超え、上限以内にあり、クレジット残高が正であることを要求します。
ルーティングフックの境界は明示的な割り当てを優先し、TenantPrivate を暗黙に選びません。
`debit_actual` は、将来実際のコストを渡せる呼び出し側が利用する、追記専用かつオーバードラフトを防ぐ引き落とし関数です。
プロバイダに依存しない需要観測、実際のコストを返す明示的なコールバック、本番ルーティング、成功後の課金は後続作業です。

## スキーマ継承の通知

リンクされた各ワークスペーススキーマが、テンプレート更新の購読単位になります。
テンプレート定義を更新すると、リンクされたスキーマの `origin_updated_at` が `NULL` になり、同じ更新を繰り返しても結果は冪等です。
MCP の upstream-change pull が検出手段で、総フィールド数、自動追加、自動更新、ローカル維持、競合数、競合フラグを含む計算済みマージ概要を返します。
競合のないマージを適用すると、新しいスキーマバージョンの作成と保留フラグの解除が同じトランザクションで行われます。
競合または失敗したマージでは通知が保留のまま残ります。

## ワークスペースのスキーマフォーク

Enterprise のワークスペースは、同じテナント内の別ワークスペースからアクティブなスキーマバージョンを正確にコピーできます。
作成には `POST /api/schema-forks` を使用します。
フォークはテンプレートの origin 追跡から切り離された状態で始まり、対象ワークスペース内に不変のスキーマ履歴を保持します。
`PUT /api/schema-forks/{fork_id}` は、ローカル定義の更新または明示的な `action=follow` のどちらか一つを受け付けます。
follow は同期的に実行され、ローカル編集を破棄する場合は `force=true` が必要です。
フォークのメタデータは、ワークスペーススキーマの系譜ではなくテンプレートライブラリ間の関係を表す `template_templates.fork_of` とは別の概念です。
